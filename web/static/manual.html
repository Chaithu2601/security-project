Operator Manual

What the scanner does, which engines it runs, and how to read the results. The web UI never scans itself — it writes your choices to a config and runs the dast_scan.py engine, which orchestrates the tools below and maps findings to OWASP Top 10 (2021) / ASVS 5.0.

Only scan systems you own or are authorised to test.

The engines we use

The harness doesn't reinvent scanners — it orchestrates best-in-class open-source tools plus its own lightweight probes. Versions below are the ones installed and verified on the scan host.

EngineVersionWhat it isHow it worksWhat we use it for
nucleiv3.9.0
tpl v10.4.6		 Fast template-driven vulnerability scanner (ProjectDiscovery). Reads YAML templates describing a request + a match condition. In -dast mode it fuzzes crawled parameters with attack payloads and matches the response; in template mode it signature-matches known CVEs/exposures/misconfigs. Both Nuclei phases: DAST injection fuzzing and CVE / exposure / misconfig scanning.
katanalatest Fast web crawler (ProjectDiscovery). Follows links, forms and JS to enumerate the app's URLs and parameters. Discovering the endpoint list every other phase feeds on (the implicit crawl).
nikto2.6.0 Classic web-server scanner. Requests a large list of known-bad paths/files and inspects banners and responses. Dangerous files, outdated server software, server misconfiguration.
testssl.sh3.2.4 Deep TLS/SSL auditor (bash). Opens many TLS handshakes to enumerate protocols, ciphers, the cert chain and known TLS CVEs. TLS / cert / cipher weaknesses (OWASP A02 / ASVS V12).
sqlmap1.10.7 Automated SQL-injection exploitation. Takes a candidate injection point and runs boolean / time / error / UNION techniques to confirm and extract. High-confidence confirmation of Nuclei's SQLi hits (optional).
OWASP ZAPDocker Full-featured web-app attack proxy. Spiders the app, then fires active attack rules through a proxy. Runs via the zaproxy/zap-stable image — no local install. Broad active scan as an alternative/complement to Nuclei DAST.
Built-in probesin engine Custom Python checks (no external tool). Direct HTTP requests + response analysis. Secret leaks, JWT/token analysis, IDOR/BOLA, CORS, CSRF/cookie flags, black-box SCA.

Every phase is guarded by a tool-availability + template-presence check, so a missing tool is skipped, not fatal.

How a scan flows

Browser form ──POST /api/scan──▶ build_config() ──▶ web/runs/<job>.yaml │ subprocess: python dast_scan.py --config <yaml> │ crawl (katana) ──▶ selected phases run ──▶ trust layer (_refine_findings) │ web/runs/projects/<name>/<date>/{REPORT.html, report.json, .md, .sarif}
  • Crawl is implicit. Any phase that needs discovered endpoints auto-enables the Katana crawl first.
  • Live output streams to the page via Server-Sent Events.
  • Abort sends a terminate signal to the engine subprocess.

Injection test types

These apply only to Nuclei DAST fuzzing. Tick the classes to fuzz — none ticked = fuzz all. Each maps to a nuclei -dast tag with real templates behind it:

sqli SQL Injection · 4 xss Cross-Site Scripting · 195 ssti Template Injection · 24 lfi Local File Inclusion · 3 ssrf Server-Side Request Forgery · 2 rce Remote Code Execution · 7 redirect Open Redirect · 2 crlf CRLF Injection · 1 xxe XML External Entity · 2

Numbers = fuzzing templates matched today (240 total). The -dast flag already scopes to fuzzing templates, so only these class tags are needed.

Trust layer — why the report is short but honest

Before writing the report, the engine's _refine_findings() step:

  • drops scanner artifacts (Nikto ARRAY(0x..) noise, testssl local-OpenSSL errors);
  • drops phantom-CMS XSS signatures Nikto invents;
  • suppresses false broken-auth "criticals" on public endpoints;
  • de-dupes and caps over-rated severities.

Each finding carries a confidence tier — confirmedfirmtentative. Tentatives are meant for human verification. No DAST tool is "100% accurate"; this harness trades raw volume for findings a customer can trust.

Troubleshooting

Target returns 504 during a scan. The 504 comes from the target's gateway (e.g. AWS CloudFront / ELB — check the response server: header), not from this tool. It means the origin can't answer in time — usually the fuzzing load is too high:

  • Abort the scan, wait ~60s, re-request the site. Recovers → it was the load.
  • Re-run with a lower rate limit + concurrency and a shallower crawl depth.
  • Prefer the light Nuclei templates pass over DAST fuzzing for a first look.
  • If it still 504s with no scan running, the site itself is down — not a tool issue.

Zero findings? Check the origin was actually up during the run — a 504-ing origin returns errors to every fuzz request, so there's nothing to match on.

ZAP does nothing? It needs Docker running (no local install).
